# ARCHITECTURE: how Quest Board fits together

Human-oriented detail, including diagrams and ADRs, is in `docs/04-technical-architecture.md` and `docs/05-data-model.md`. This file is the working map.

## Stack
- **Framework:** Next.js 16 App Router, React 19, TypeScript strict, Tailwind v4.
- **Data:** SQLite through Node's built-in `node:sqlite`, with a single process-wide connection in WAL mode.
- **Auth:** custom scrypt password hashes plus DB-backed sessions. The `qb_session` cookie stores the token; the DB stores only its SHA-256 hash.
- **Icons:** Flaticon UIcons, subset into a small font by `scripts/build-icons.mjs`.
- **Runtime:** Node ≥ 22.13 (developed on 24). Runtime dependencies are `next`, `react`, `react-dom`, `server-only` and `@flaticon/flaticon-uicons` (used as build input only).

## Request lifecycle
- **Read:** a server component awaits `params`, then calls `getI18n()`, `getCurrentUser()` (memoised per request) and the synchronous `queries.ts` functions, and renders HTML. Client components hydrate only forms and `<LocalTime>`.
- **Write:** a `<form action={serverAction}>` sends the request. The exported action wraps an internal `…Impl` in `withEcho()`. The impl validates (returning `MsgKey` errors), rate-limits (`hit()`), authorizes, writes the DB (inside `tx()` if capacity is involved), calls `revalidatePath("/", "layout")`, and then either redirects or returns `{ ok }`. On failure, `withEcho` adds `values` so the form can refill itself after React's automatic reset.

## Data model (schema v8)
| Table | Contents |
|---|---|
| `users` | `role` is `player`, `gm` or `admin`; `avatar_image` (optional path, v6) |
| `gm_profiles` | `headline`, `systems`, `years_experience`, **`location`**, `verified`, **`payment_info`** (members-only) |
| `auth_sessions` | `token_hash`, `user_id`, `expires_at` |
| `games` | `cover_image` (optional path, v6), `price_idr`, `seats_total` (1–12), `format`, `location_type` + `platform`/`city`, **`language`** (`id`\|`en`\|`both`), `status` (`draft`\|`published`\|`archived`), **`genres`/`styles`** (CSV of category keys, max 3 each, v7) |
| `game_sessions` | `starts_at` UTC, `status` (`scheduled`\|`completed`\|`cancelled`) |
| `bookings` | `status` (`confirmed`\|`cancelled`), `cancelled_by`, `price_idr` snapshot. Unique active seat per (session, player) |
| `reviews` | one per (game, player) |
| `messages` | table chat (the page shows the newest 200) |
| `gm_requests` | `requester_id`, `gm_id` (NULL = open to all GMs), title/system/group_size/level/language/location/schedule/budget_idr/details, `status` (`open`\|`matched`\|`closed`), `matched_gm_id` (v7) |
| `gm_request_offers` | `message`, `price_idr` (per player per session); UNIQUE(request_id, gm_id) (v7) |
| `gm_request_messages` | private thread between the requester and the matched GM (v7) |
| `notifications` | `user_id`, `kind`, `actor_id`, `request_id`/`session_id` (link target), `read_at` (v8). Written only through `notify()` |
| `rate_limits` | `key` = `<bucket>:<identity>`, `window_start`, `count` (v5) |

Derived values (seats taken, ratings, expected income) are computed in SQL inside `queries.ts`. They are not stored.

## Invariants (don't break these)
1. **Seat capacity** is re-checked by `canBook()` inside `tx()`, under `BEGIN IMMEDIATE`. The partial unique index `uq_booking_active` is a backstop.
2. **Membership** is `isGameMember()`: the owning GM, or a player with a confirmed seat. It gates the table chat and the payment-details card.
3. **Payment details** are selected in `getGameBySlug()` for convenience, but rendered only when `member && user.id !== gm_id`. **Never add them to the API routes, `GameCard` or the GM profile page.**
4. **Reviews** are allowed only after the player has held a seat in a session that has started, and only once per game.
5. **The language** comes only from the `qb_lang` cookie, defaulting to `en`. There is no URL prefix and no Accept-Language detection.
6. **Seats never drop below bookings.** Editing `seats_total` is checked against `maxSeatsTakenUpcoming()`. Archiving cancels future sessions.
7. **Never wipe data in production.** Schema changes ship as migrations (see below).
8. **Images are allow-listed.** `saveGameAction` accepts only `isAllowedCover(value, current)` and `becomeGmAction` only `isAllowedPortrait(value, current)`: `""`, a library path, or the current value. Never store a user-supplied URL.

## Recipes
- **New demo artwork:**
  1. Add an entry to `COVER_ART` (slug → motif + hue) or `GM_PORTRAITS` in `src/lib/placeholders.ts`.
  2. For a new motif, add a drawing function to `motifs` in `scripts/build-placeholders.mjs`.
  3. Run `npm run placeholders` and commit `public/images/*`.
  4. For databases that already exist, add a migration that back-fills the path. Existing migrations are frozen.
- **Showing images:** `<Cover image={…}>`, `<Avatar image={…}>` and `<Thumb image={…}>` fall back to the gradient or initials when the image is empty. They use `next/image` with `fill`; `.svg` files are served unoptimised automatically.
- **New UI string:** add the key to `en` and `id` in `dict.ts`, then use `t("ns.key")`.
- **New icon:** add the name to `REGULAR_ICONS` or `SOLID_ICONS` in `src/lib/icons.ts`, run `npm run icons`, commit `src/app/icons/*`, then use `<Icon name="…" />`. Browse available names at flaticon.com/uicons.
- **New game field:**
  1. Add the column in `schema.ts` and bump `SCHEMA_VERSION`.
  2. Update `GameInput` and `parseGame` in `validation.ts`.
  3. Add the column to the INSERT/UPDATE in `saveGameAction`.
  4. Update `GameRow`/`GameCard` and the SQL in `queries.ts`.
  5. Update `game-form.tsx` defaults and fields, and `EMPTY_GAME`.
  6. Update the edit page defaults, `seed.ts`, the API mapping if the field is public, and `dict.ts` labels.
  7. Update the tests and `docs/05`.
- **New category (genre or style):**
  1. Add `{ key, icon }` to `GENRES` or `STYLES` in `lib/categories.ts`. Add the icon to `icons.ts` if needed, and run `npm run icons`.
  2. Add `genre.<key>` and `genreDesc.<key>` (or `style.*`) to both dictionaries. The unit test checks this.
  3. Keys are stored in the DB, so never rename one; add a new key and migrate instead.
- **New system blurb:** add the slug to `SYSTEM_BLURBS` and `systemDesc.<slug>` to both dictionaries.
- **Who can see a GM request:** the logic lives in `hire-a-gm/requests/[id]/page.tsx` (view) and the request actions (write). Keep the two in sync, and never show `payment_info` to anyone but the requester after a match.
- **New notification kind:**
  1. Add it to `NotificationKind` in `lib/notifications.ts` (and to `COLLAPSE` if it's chatty).
  2. Call `notify({...}, c)` in the action. Pass `c` when inside `tx()`. It never notifies the actor.
  3. Add a case to `describeNotification()` in `lib/notification-view.ts` (shared by the popover and the page) and `notif.*` strings in both dictionaries.
- **Form fields:** render errors with `<FieldError id="x" msg={…} />` and spread `{...errAttrs("x", msg)}` on the control, so screen readers announce the error.
- **New server action:** add it to `actions.ts` with its own auth check. Return `FormState` with `MsgKey` errors, and call `revalidatePath("/", "layout")`.
- **New page:** `src/app/<route>/page.tsx` as an async server component, with `generateMetadata()` using `t()` and a guard via `requireUser()` or `requireGm()` if it's private.

## Schema & migrations
`PRAGMA user_version` is the ledger, and `db.ts → prepareSchema()` asks `planSchemaUpgrade()` (in `migrations.ts`) what to do:

| Plan | When | Action |
|---|---|---|
| `fresh` | empty DB | run `SCHEMA_SQL` (the current full schema), set the version, seed |
| `none` | DB at `SCHEMA_VERSION` | nothing |
| `migrate` | a migration exists for every step | run each `MIGRATIONS[v]` in its own transaction and bump `user_version`. **Data is kept** |
| `reset` | no migration path (pre-v4 demo DBs), **development only** | `VACUUM INTO <file>.v<N>.bak`, drop the tables, then recreate |
| `error` | production without a migration path, or a DB newer than the code | refuse to start. `QUESTBOARD_ALLOW_RESET=true` overrides |

**Recipe: change the schema**
1. Edit `SCHEMA_SQL` for fresh databases.
2. Add `MIGRATIONS[n+1]` for existing ones, written to preserve data (`ALTER TABLE … ADD COLUMN`, `CREATE … IF NOT EXISTS`).
3. Bump `SCHEMA_VERSION`, then update `seed.ts` and `docs/05`.

A unit test checks that every version after the baseline has a migration.
